# Отчёт об ошибках и багах Miniage v2

Дата: 2026-11-27. Проверялась игровая логика и клиентская часть после аудита
безопасности (`SECURITY.md`).

Методика: сквозные сценарии через живой HTTP API + изолированный PHP-харнесс
в php-wasm (SQLite в памяти), 16 автоматических проверок.

## Итог

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 1 | Отступление (`flee`) сбрасывало респавн монстра | **Критический** | исправлено |
| 2 | Мёртвого персонажа воскрешала смена экипировки | Высокая | исправлено |
| 3 | Мёртвого поднимало обычное зелье лечения | Высокая | исправлено |
| 4 | `heal` мёртвого падал с «уже полностью здоров» | Высокая | исправлено |

## Критический: эксплойт бесконечной охоты

`isMobAlive()` определял время победы по `updated_at` — полю, которое меняется
при **любом** обновлении строки боя. Достаточно было после победы вызвать
`/api/battle/flee`, который писал `state = 'fled'` и обновлял `updated_at`,
и респавн обнулялся.

Замер до фикса: 3 убийства за 0,5 секунды при штатном респавне 18 секунд —
**рост адены и опыта в ~100 раз быстрее нормального**.

Исправление:
- новая колонка `battles.won_at`, заполняется только при победе;
- респавн считается от неё, а не от `updated_at`;
- `flee` теперь работает только из активного боя (`state = 'active'`),
  завершённый бой перевести в `fled` нельзя;
- догоняющая миграция `Migrator::upgrade()` добавляет колонку в существующие
  базы (с `ALTER TABLE`), заполняя её значением `updated_at`.

Проверено: после победы повторный старт боя даёт «Монстр ещё не возродился»,
`flee` по выигранному бою — «Бой уже завершён».

## Высокие: смерть персонажа

Три связанных бага делали смерть либо бессмысленной, либо тупиковой:

**2. Воскрешение экипировкой.** `recalcStats()` подставлял полный HP, если
текущий был `<= 0`:

```php
'hp' => min((int) $char['hp'] > 0 ? (int) $char['hp'] : $hpMax, $hpMax),
```

Снять и надеть предмет — и персонаж снова жив. Теперь `hp` просто зажимается
в `0..hp_max`, мёртвый остаётся мёртвым.

**3. Зелье как воскрешение.** `useItem()` не проверял, жив ли персонаж:
зелье поднимало HP с 0 до максимума, хотя реанимация задумана платной (500
адены). Добавлен отказ: «Персонаж мёртв — нужна реанимация в городе».

**4. `heal` отказывал мёртвому.** Проверка «уже полностью здоров» стояла
раньше проверки смерти, а у мёртвого `hp = 0 < hp_max`, но `mp` мог быть
полным... точнее, условие требовало одновременно полных HP и MP, поэтому
срабатывало при полном MP — и мёртвый получал отказ вместо реанимации.
Теперь мёртвый сразу уходит в ветку реанимации, а проверка «здоров»
применяется только к живым.

## Средние

**5. Зелье впустую.** При полном HP/MP предмет удалялся из инвентаря, ничего
не восстанавливая. Теперь отказ, количество не уменьшается.

**6. Левелап и экипировка.** `applyRewards()` прибавлял `+12+2·lvl` к
`hp_max`, который уже содержал бонусы надетых предметов. Затем ближайшая
смена экипировки вызывала `recalcStats()`, пересчитывающий статы с нуля, и
накопленный прирост исчезал. Теперь после повышения уровня вызывается
`recalcStats()` (единая формула «база за уровень + бонусы»), а затем HP/MP
восстанавливаются до нового максимума.

Проверено: после победы `hp_max` = 156, принудительный `recalcStats` даёт те
же 156 (согласовано), при следующем уровне — 174.

**7. Фантомная регенерация.** Клиент каждые 5 секунд увеличивал HP/MP в
локальном состоянии и перерисовывал HUD. Сервер об этом не знал: полоса
показывала восстановление, но в бою и при лечении использовались старые
значения. Реализовано на сервере: `GameService::applyRegen()` начисляет
0,2 % от максимума в секунду (не более минуты за раз) при чтении персонажа,
мёртвых не трогает. Клиент теперь только подтягивает актуальные числа через
`/api/bootstrap` раз в 10 секунд.

**8. Стартовый капитал.** В обеих схемах `adena DEFAULT 30000000`. Каждый
новичок начинал с 30 млн — экономика обессмысливалась. Стало 500. Демо-аккаунт
`demo` по-прежнему получает 30 млн, чтобы магазин можно было посмотреть сразу.

**9. Нет валидации расы/класса.** `POST /api/register` с
`race=<script>alert(1)</script>` и `class=godmode` создавал персонажа; в БД
попадала HTML-строка, статы при этом брались как у воина. Добавлен белый
список: `AuthService::RACES`, `AuthService::CLASSES`, пол — `m`/`f`.

## Низкий

**10. `flee` по завершённому бою** перезаписывал `won`/`lost` на `fled`,
портя статистику. Закрыто вместе с багом 1.

## Проверено и в порядке

| Сценарий | Результат |
|---|---|
| Повторная экипировка того же предмета | статы не удваиваются |
| Дубль предметов в одном слоте | невозможен, старый снимается |
| Продажа надетого предмета | отказ «Сначала снимите предмет» |
| `battle_id` = 0, −5, 999999999 | «Бой не найден» |
| Чужой бой / чужой инвентарь / чужой персонаж | `403` / `404` |
| Битый JSON в теле | `419`, без 500 |
| Кириллица в логине | отказ по формату |
| Пустые/огромные `qty` в buy/sell | клампятся |
| Координаты вне карты в `move` | клампятся в 0..900 / 0..560 |
| Гонка: 8 параллельных ударов | награда не дублируется |
| Магазин, чат, рейтинг, новости, статика | 200 |

## Как перепроверить

Логический харнесс прогоняется в php-wasm (SQLite в памяти), живой сервер не
нужен:

```bash
cd v2/preview
node logic.mjs      # 16 проверок: T1..T10, ожидаемый вывод — все OK
```

Живая проверка эксплойта:

```bash
# 1) убить моба, 2) отступить, 3) снова начать бой — должно быть "не возродился"
curl -s -b jar -X POST localhost:3000/api/battle/flee \
     -H 'Content-Type: application/json' -d '{"battle_id":1,"_csrf":"..."}'
```

## Остаточное

1. **Демо-аккаунт с 30 млн адены** остаётся витриной. В проде `SEED_DEMO=0`.
2. **Регенерация офлайн.** `applyRegen()` ограничен 60 секундами за один
   расчёт, поэтому после долгого отсутствия персонаж не получает HP «пачкой».
   Это осознанное решение, а не баг.
3. **Смерть наказывает только потерей времени** (реанимация 500 адены).
   Опыт и предметы не отнимаются — так было и в legacy.
