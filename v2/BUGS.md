# Отчёт об ошибках и багах Miniage v2

Дата: 2026-11-27. Проверялась игровая логика и клиентская часть после аудита
безопасности (`SECURITY.md`).

Методика: сквозные сценарии через живой HTTP API + изолированный PHP-харнесс
в php-wasm (SQLite в памяти), 16 автоматических проверок.

## Итог

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 1 | Отступление (`flee`) сбрасывало респавн монстра | **Критический** | исправлено |
| 2 | Мёртвого персонажа воскрешала смена экипировки | Высокая | исправлено |
| 3 | Мёртвого поднимало обычное зелье лечения | Высокая | исправлено |
| 4 | `heal` мёртвого падал с «уже полностью здоров» | Высокая | исправлено |
| 5 | Зелье тратилось впустую при полном HP/MP | Средняя | исправлено |
| 6 | Левелап «съедал» бонусы экипировки | Средняя | исправлено |
| 7 | Клиент рисовал регенерацию, которой не было на сервере | Средняя | исправлено |
| 8 | Новичок получал 30 000 000 адены | Средняя | исправлено |
| 9 | Раса/класс/пол не валидировались (HTML в БД) | Средняя | исправлено |
| 10 | `flee` перезаписывал исход завершённого боя | Низкая | исправлено |

## Критический: эксплойт бесконечной охоты

`isMobAlive()` определял время победы по `updated_at` — полю, которое меняется
при **любом** обновлении строки боя. Достаточно было после победы вызвать
`/api/battle/flee`, который писал `state = 'fled'` и обновлял `updated_at`,
и респавн обнулялся.

Замер до фикса: 3 убийства за 0,5 секунды при штатном респавне 18 секунд —
**рост адены и опыта в ~100 раз быстрее нормального**.

Исправление:
- новая колонка `battles.won_at`, заполняется только при победе;
- респавн считается от неё, а не от `updated_at`;
- `flee` теперь работает только из активного боя (`state = 'active'`),
  завершённый бой перевести в `fled` нельзя;
- догоняющая миграция `Migrator::upgrade()` добавляет колонку в существующие
  базы (с `ALTER TABLE`), заполняя её значением `updated_at`.

Проверено: после победы повторный старт боя даёт «Монстр ещё не возродился»,
`flee` по выигранному бою — «Бой уже завершён».

## Высокие: смерть персонажа

Три связанных бага делали смерть либо бессмысленной, либо тупиковой:

**2. Воскрешение экипировкой.** `recalcStats()` подставлял полный HP, если
текущий был `<= 0`:

```php
'hp' => min((int) $char['hp'] > 0 ? (int) $char['hp'] : $hpMax, $hpMax),
```

Снять и надеть предмет — и персонаж снова жив. Теперь `hp` просто зажимается
в `0..hp_max`, мёртвый остаётся мёртвым.

**3. Зелье как воскрешение.** `useItem()` не проверял, жив ли персонаж:
зелье поднимало HP с 0 до максимума, хотя реанимация задумана платной (500
адены). Добавлен отказ: «Персонаж мёртв — нужна реанимация в городе».

**4. `heal` отказывал мёртвому.** Проверка «уже полностью здоров» стояла
раньше проверки смерти, а у мёртвого `hp = 0 < hp_max`, но `mp` мог быть
полным... точнее, условие требовало одновременно полных HP и MP, поэтому
срабатывало при полном MP — и мёртвый получал отказ вместо реанимации.
Теперь мёртвый сразу уходит в ветку реанимации, а проверка «здоров»
применяется только к живым.

## Средние

**5. Зелье впустую.** При полном HP/MP предмет удалялся из инвентаря, ничего
не восстанавливая. Теперь отказ, количество не уменьшается.

**6. Левелап и экипировка.** `applyRewards()` прибавлял `+12+2·lvl` к
`hp_max`, который уже содержал бонусы надетых предметов. Затем ближайшая
смена экипировки вызывала `recalcStats()`, пересчитывающий статы с нуля, и
накопленный прирост исчезал. Теперь после повышения уровня вызывается
`recalcStats()` (единая формула «база за уровень + бонусы»), а затем HP/MP
восстанавливаются до нового максимума.

Проверено: после победы `hp_max` = 156, принудительный `recalcStats` даёт те
же 156 (согласовано), при следующем уровне — 174.

**7. Фантомная регенерация.** Клиент каждые 5 секунд увеличивал HP/MP в
локальном состоянии и перерисовывал HUD. Сервер об этом не знал: полоса
показывала восстановление, но в бою и при лечении использовались старые
значения. Реализовано на сервере: `GameService::applyRegen()` начисляет
0,2 % от максимума в секунду (не более минуты за раз) при чтении персонажа,
мёртвых не трогает. Клиент теперь только подтягивает актуальные числа через
`/api/bootstrap` раз в 10 секунд.

**8. Стартовый капитал.** В обеих схемах `adena DEFAULT 30000000`. Каждый
новичок начинал с 30 млн — экономика обессмысливалась. Стало 500. Демо-аккаунт
`demo` по-прежнему получает 30 млн, чтобы магазин можно было посмотреть сразу.

**9. Нет валидации расы/класса.** `POST /api/register` с
`race=<script>alert(1)</script>` и `class=godmode` создавал персонажа; в БД
попадала HTML-строка, статы при этом брались как у воина. Добавлен белый
список: `AuthService::RACES`, `AuthService::CLASSES`, пол — `m`/`f`.

## Низкий

**10. `flee` по завершённому бою** перезаписывал `won`/`lost` на `fled`,
портя статистику. Закрыто вместе с багом 1.

## Проверено и в порядке

| Сценарий | Результат |
|---|---|
| Повторная экипировка того же предмета | статы не удваиваются |
| Дубль предметов в одном слоте | невозможен, старый снимается |
| Продажа надетого предмета | отказ «Сначала снимите предмет» |
| `battle_id` = 0, −5, 999999999 | «Бой не найден» |
| Чужой бой / чужой инвентарь / чужой персонаж | `403` / `404` |
| Битый JSON в теле | `419`, без 500 |
| Кириллица в логине | отказ по формату |
| Пустые/огромные `qty` в buy/sell | клампятся |
| Координаты вне карты в `move` | клампятся в 0..900 / 0..560 |
| Гонка: 8 параллельных ударов | награда не дублируется |
| Магазин, чат, рейтинг, новости, статика | 200 |

## Как перепроверить

Логический харнесс прогоняется в php-wasm (SQLite в памяти), живой сервер не
нужен:

```bash
cd v2/preview
node logic.mjs      # 16 проверок: T1..T10, ожидаемый вывод — все OK
```

Живая проверка эксплойта:

```bash
# 1) убить моба, 2) отступить, 3) снова начать бой — должно быть "не возродился"
curl -s -b jar -X POST localhost:3000/api/battle/flee \
     -H 'Content-Type: application/json' -d '{"battle_id":1,"_csrf":"..."}'
```

## Остаточное

1. **Демо-аккаунт с 30 млн адены** остаётся витриной. В проде `SEED_DEMO=0`.
2. **Регенерация офлайн.** `applyRegen()` ограничен 60 секундами за один
   расчёт, поэтому после долгого отсутствия персонаж не получает HP «пачкой».
   Это осознанное решение, а не баг.
3. **Смерть наказывает только потерей времени** (реанимация 500 адены).
   Опыт и предметы не отнимаются — так было и в legacy.

# Второй проход (конкурентность, целостность, данные)

Дата: 2026-11-27, после первого раунда исправлений. Проверялись гонки,
граничные значения, производительность и накопление данных.

## Итог второго прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 11 | Чат с длинной кириллицей ломал `json_encode` — ответ `{"ok":false,"error":"json_encode"}` | **Критический** | исправлено |
| 12 | Логины различались по регистру: `demo`, `Demo`, `DEMO` — разные игроки | Высокая | исправлено |
| 13 | `HEAD /` возвращал 404 | Средняя | исправлено |
| 14 | Неизвестный канал чата молча отдавал пустой список | Средняя | исправлено |
| 15 | Нет лимита размера тела запроса | Средняя | исправлено |
| 16 | Сессии, бои и попытки входа копились вечно | Средняя | исправлено |
| 17 | Битый UTF-8 в любом ответе API отдавал бесполезную заглушку | Средняя | исправлено |

## Критический: чат ломал ответ

Сообщение из 300 кириллических символов возвращало
`{"ok":false,"error":"json_encode"}`. Причина — двойная ошибка:

1. В `ChatService` обрезка `substr($text, 0, 240)` резала многобайтовый
   символ на середине, оставляя невалидный UTF-8.
2. Следующий «трим» хвостовых байт отрезал ещё больше, но граница уже была
   потеряна — строка оставалась битой.
3. `json_encode()` возвращал `false`, и `Response::json` подставлял
   бесполезную заглушку.

Исправлено на трёх уровнях:
- `ChatService::limitUtf8()` — обрезка идёт **от начала**, копит только целые
  символы (1–4 байта), битые байты пропускает;
- `Response::json()` при `json_encode === false` теперь чистит данные
  (`scrubUtf8`), затем повторяет кодирование с `JSON_INVALID_UTF8_SUBSTITUTE`
  и логирует причину, вместо молчаливой заглушки;
- константа `MAX_LEN = 240` вместо магических чисел.

Проверено: 300 символов «Ж» → 240 символов, `ok: true`; 300 эмодзи → OK.

## Высокая: регистр логинов

MySQL сравнивает ник без учёта регистра (`utf8mb4_unicode_ci`), SQLite — с
учётом. Из-за этого в превью заводились `demo`, `Demo` и `DEMO` как разные
игроки, а на проде те же данные вели бы себя иначе.

Исправление: `AuthService::normalizeNick()` + проверка уникальности по всем
записям и запасной поиск при входе. Теперь `DEMO` при существующем `demo` →
«Такой логин уже занят», а вход `Demo`/`demo` находит один и тот же аккаунт.

## Средние

**13. HEAD → 404.** Роутер сравнивал метод строго. Теперь `HEAD`
обслуживается как `GET`, но `Response::send()` не отдаёт тело — как требует
стандарт. Нужно для мониторинга и кэширующих прокси.

**14. Неизвестный канал чата** возвращал `ok: true` и пустой список —
пользователь видел «пустой чат» вместо ошибки. Теперь `400`
`chat_channel`, отрицательный `after` зажимается в 0.

**15. Нет лимита тела.** 2 МБ JSON принимались и разбирались. Добавлен
`Request::MAX_BODY = 1 MiB` и проверка в `Router::dispatch()` до разбора:
ответ `413 too_large`.

**16. Накопление данных.** Каждая анонимная загрузка страницы создавала
строку в `sessions`, каждый бой — в `battles`; чистки не было. Добавлен
`Migrator::gc()`: удаляет сессии старше `SESSION_TTL`, завершённые бои старше
суток, попытки входа старше суток. Запускается с вероятностью 1/50 на запрос
(и принудительно через `gc(true)` в тестах), ошибки уборки не роняют запрос.

**17. Битый UTF-8** из любого источника (не только чата) теперь не убивает
ответ: см. `Response::json()` выше.

## Проверено во втором проходе и в порядке

| Сценарий | Результат |
|---|---|
| Гонка при покупке: 6 параллельных при 500 адены | 1 успех, адена 50, в минус не ушла |
| Гонка: 10 параллельных ударов до победы | ровно 1 `won`, награда один раз |
| Регистр ников: `DEMO`/`dEmO` при существующем `demo` | отказ |
| Чат 300 «Ж», 300 эмодзи | 240 символов, `json_encode` OK |
| `after=-100`, `after=abc` | зажимается в 0, без ошибок |
| Продажа `qty=0` / отрицательное | кламп в 1 |
| `move` с городом не из списка | сбрасывается в `Giran` |
| Покупка несуществующего / не по уровню | понятные ошибки |
| Логаут | сессия уничтожена, аккаунт не виден |

# Третий проход (iframe-режим, прод-конфигурация, типы входных данных)

Дата: 2026-11-27. Проверялись резервный путь сессии без cookie, запуск с
`SEED_DEMO=0`, миграция старой базы и приведение типов из JSON.

## Итог третьего прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 18 | `?s=` fallback не работал: сервер искал `miniage_sid`, клиент слал `s` | **Критический** | исправлено |
| 19 | `SEED_DEMO=0` отключал ВСЮ инициализацию — игра без предметов и мобов | **Критический** | исправлено |
| 20 | Легаси-редиректы теряли `?s=` — сессия обрывалась в iframe | Высокая | исправлено |
| 21 | `equip:"false"` (строка) приводился к `true` — предмет надевался вместо снятия | Средняя | исправлено |
| 22 | `text={...}` попадал в чат как слово «Array» | Средняя | исправлено |
| 23 | `loadZone` падал с TypeError при `state.char === null` | Низкая | исправлено |
| 24 | Деление на ноль в HUD при `hp_max = 0` | Низкая | исправлено |
| 25 | Магазин не обновлялся после покупки | Низкая | исправлено |

## Критический: резервная сессия не работала

Клиент (`api.js`, `PageController`) передаёт sid коротким параметром `?s=`,
а `Session::start()` искал только `?miniage_sid=`. Резервный путь **не
срабатывал никогда**. В обычном браузере это незаметно (работают cookie и
заголовок), но в iframe с заблокированными cookie — то есть в превью и
приватном режиме — игра была недоступна: каждая загрузка давала новую
сессию, вход «терялся».

Исправление: принимаются оба имени (`s` и `miniage_sid`), выставлен
`in_url = true`. Проверен полный сценарий без cookie: страница → bootstrap →
вход → персонаж → бой → чат.

## Критический: `SEED_DEMO=0` ломал игру

`Migrator::seed()` начинался с:

```php
if (Config::get('SEED_DEMO', '1') !== '1') {
    return;   // отключает ВСЁ
}
```

а `.env.example` и `SECURITY.md` советуют для прода `SEED_DEMO=0`. В итоге на
проде не создавались уровни, предметы, монстры и новости — игра пустая.

Исправление: `seed()` всегда создаёт контент (уровни, предметы, мобы,
новости), а флаг влияет только на демо-аккаунты. Добавлен `seedNews()`.

Проверено с `APP_ENV=production, SEED_DEMO=0`: `level_exp` 50, `items` 14,
`mobs` 10, `news` 2, `accounts` 0; регистрация и стартовый набор работают.

## Высокая: редиректы теряли sid

`gorod.php?s=…` → `/?panel=map` без `s`. В iframe это обрывало сессию на
любой старой ссылке. Теперь `s` переносится (с валидацией формата).

## Средние: приведение типов

**`equip:"false"`.** `(bool) 'false'` в PHP — это `true`, поэтому строка
`"false"` **надевала** предмет вместо снятия. Клиент шлёт настоящий boolean,
но любой другой клиент/скрипт попадал в ловушку. Добавлен `toBool()`:
принимает `bool`, `0/1`, `'true'/'false'/'on'/'yes'`.

**`text={...}`.** `(string)` от массива в PHP 8 даёт `"Array"` (с warning),
и в чат попадало слово «Array». Добавлены `Request::str()` и
`Request::intInput()`: не-скаляры превращаются в пустую строку/0, все
обработчики переведены на них.

## Низкие (клиент)

- `loadZone` читал `state.char.level` без проверки на `null` → `TypeError`,
  если зона грузится до входа.
- `updateHud` делил на `hp_max`/`mp_max` без защиты — при 0 получался `NaN`
  в `style.width`.
- После покупки магазин не перерисовывался: экран показывал старые данные,
  хотя аде­на уже списана.

|---|---|

| Повторный `migrate()` | идемпотентен |
