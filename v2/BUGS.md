# Отчёт об ошибках и багах Miniage v2

Дата: 2026-11-27. Проверялась игровая логика и клиентская часть после аудита
безопасности (`SECURITY.md`).

Методика: сквозные сценарии через живой HTTP API + изолированный PHP-харнесс
в php-wasm (SQLite в памяти), 16 автоматических проверок.

## Итог

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 1 | Отступление (`flee`) сбрасывало респавн монстра | **Критический** | исправлено |
| 2 | Мёртвого персонажа воскрешала смена экипировки | Высокая | исправлено |
| 3 | Мёртвого поднимало обычное зелье лечения | Высокая | исправлено |
| 4 | `heal` мёртвого падал с «уже полностью здоров» | Высокая | исправлено |
| 5 | Зелье тратилось впустую при полном HP/MP | Средняя | исправлено |
| 6 | Левелап «съедал» бонусы экипировки | Средняя | исправлено |
| 7 | Клиент рисовал регенерацию, которой не было на сервере | Средняя | исправлено |
| 8 | Новичок получал 30 000 000 адены | Средняя | исправлено |
| 9 | Раса/класс/пол не валидировались (HTML в БД) | Средняя | исправлено |
| 10 | `flee` перезаписывал исход завершённого боя | Низкая | исправлено |

## Критический: эксплойт бесконечной охоты

`isMobAlive()` определял время победы по `updated_at` — полю, которое меняется
при **любом** обновлении строки боя. Достаточно было после победы вызвать
`/api/battle/flee`, который писал `state = 'fled'` и обновлял `updated_at`,
и респавн обнулялся.

Замер до фикса: 3 убийства за 0,5 секунды при штатном респавне 18 секунд —
**рост адены и опыта в ~100 раз быстрее нормального**.

Исправление:
- новая колонка `battles.won_at`, заполняется только при победе;
- респавн считается от неё, а не от `updated_at`;
- `flee` теперь работает только из активного боя (`state = 'active'`),
  завершённый бой перевести в `fled` нельзя;
- догоняющая миграция `Migrator::upgrade()` добавляет колонку в существующие
  базы (с `ALTER TABLE`), заполняя её значением `updated_at`.

Проверено: после победы повторный старт боя даёт «Монстр ещё не возродился»,
`flee` по выигранному бою — «Бой уже завершён».

## Высокие: смерть персонажа

Три связанных бага делали смерть либо бессмысленной, либо тупиковой:

**2. Воскрешение экипировкой.** `recalcStats()` подставлял полный HP, если
текущий был `<= 0`:

```php
'hp' => min((int) $char['hp'] > 0 ? (int) $char['hp'] : $hpMax, $hpMax),
```

Снять и надеть предмет — и персонаж снова жив. Теперь `hp` просто зажимается
в `0..hp_max`, мёртвый остаётся мёртвым.

**3. Зелье как воскрешение.** `useItem()` не проверял, жив ли персонаж:
зелье поднимало HP с 0 до максимума, хотя реанимация задумана платной (500
адены). Добавлен отказ: «Персонаж мёртв — нужна реанимация в городе».

**4. `heal` отказывал мёртвому.** Проверка «уже полностью здоров» стояла
раньше проверки смерти, а у мёртвого `hp = 0 < hp_max`, но `mp` мог быть
полным... точнее, условие требовало одновременно полных HP и MP, поэтому
срабатывало при полном MP — и мёртвый получал отказ вместо реанимации.
Теперь мёртвый сразу уходит в ветку реанимации, а проверка «здоров»
применяется только к живым.

## Средние

**5. Зелье впустую.** При полном HP/MP предмет удалялся из инвентаря, ничего
не восстанавливая. Теперь отказ, количество не уменьшается.

**6. Левелап и экипировка.** `applyRewards()` прибавлял `+12+2·lvl` к
`hp_max`, который уже содержал бонусы надетых предметов. Затем ближайшая
смена экипировки вызывала `recalcStats()`, пересчитывающий статы с нуля, и
накопленный прирост исчезал. Теперь после повышения уровня вызывается
`recalcStats()` (единая формула «база за уровень + бонусы»), а затем HP/MP
восстанавливаются до нового максимума.

Проверено: после победы `hp_max` = 156, принудительный `recalcStats` даёт те
же 156 (согласовано), при следующем уровне — 174.

**7. Фантомная регенерация.** Клиент каждые 5 секунд увеличивал HP/MP в
локальном состоянии и перерисовывал HUD. Сервер об этом не знал: полоса
показывала восстановление, но в бою и при лечении использовались старые
значения. Реализовано на сервере: `GameService::applyRegen()` начисляет
0,2 % от максимума в секунду (не более минуты за раз) при чтении персонажа,
мёртвых не трогает. Клиент теперь только подтягивает актуальные числа через
`/api/bootstrap` раз в 10 секунд.

**8. Стартовый капитал.** В обеих схемах `adena DEFAULT 30000000`. Каждый
новичок начинал с 30 млн — экономика обессмысливалась. Стало 500. Демо-аккаунт
`demo` по-прежнему получает 30 млн, чтобы магазин можно было посмотреть сразу.

**9. Нет валидации расы/класса.** `POST /api/register` с
`race=<script>alert(1)</script>` и `class=godmode` создавал персонажа; в БД
попадала HTML-строка, статы при этом брались как у воина. Добавлен белый
список: `AuthService::RACES`, `AuthService::CLASSES`, пол — `m`/`f`.

## Низкий

**10. `flee` по завершённому бою** перезаписывал `won`/`lost` на `fled`,
портя статистику. Закрыто вместе с багом 1.

## Проверено и в порядке

| Сценарий | Результат |
|---|---|
| Повторная экипировка того же предмета | статы не удваиваются |
| Дубль предметов в одном слоте | невозможен, старый снимается |
| Продажа надетого предмета | отказ «Сначала снимите предмет» |
| `battle_id` = 0, −5, 999999999 | «Бой не найден» |
| Чужой бой / чужой инвентарь / чужой персонаж | `403` / `404` |
| Битый JSON в теле | `419`, без 500 |
| Кириллица в логине | отказ по формату |
| Пустые/огромные `qty` в buy/sell | клампятся |
| Координаты вне карты в `move` | клампятся в 0..900 / 0..560 |
| Гонка: 8 параллельных ударов | награда не дублируется |
| Магазин, чат, рейтинг, новости, статика | 200 |

## Как перепроверить

Логический харнесс прогоняется в php-wasm (SQLite в памяти), живой сервер не
нужен:

```bash
cd v2/preview
node logic.mjs      # 16 проверок: T1..T10, ожидаемый вывод — все OK
```

Живая проверка эксплойта:

```bash
# 1) убить моба, 2) отступить, 3) снова начать бой — должно быть "не возродился"
curl -s -b jar -X POST localhost:3000/api/battle/flee \
     -H 'Content-Type: application/json' -d '{"battle_id":1,"_csrf":"..."}'
```

## Остаточное

1. **Демо-аккаунт с 30 млн адены** остаётся витриной. В проде `SEED_DEMO=0`.
2. **Регенерация офлайн.** `applyRegen()` ограничен 60 секундами за один
   расчёт, поэтому после долгого отсутствия персонаж не получает HP «пачкой».
   Это осознанное решение, а не баг.
3. **Смерть наказывает только потерей времени** (реанимация 500 адены).
   Опыт и предметы не отнимаются — так было и в legacy.

# Второй проход (конкурентность, целостность, данные)

Дата: 2026-11-27, после первого раунда исправлений. Проверялись гонки,
граничные значения, производительность и накопление данных.

## Итог второго прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 11 | Чат с длинной кириллицей ломал `json_encode` — ответ `{"ok":false,"error":"json_encode"}` | **Критический** | исправлено |
| 12 | Логины различались по регистру: `demo`, `Demo`, `DEMO` — разные игроки | Высокая | исправлено |
| 13 | `HEAD /` возвращал 404 | Средняя | исправлено |
| 14 | Неизвестный канал чата молча отдавал пустой список | Средняя | исправлено |
| 15 | Нет лимита размера тела запроса | Средняя | исправлено |
| 16 | Сессии, бои и попытки входа копились вечно | Средняя | исправлено |
| 17 | Битый UTF-8 в любом ответе API отдавал бесполезную заглушку | Средняя | исправлено |

## Критический: чат ломал ответ

Сообщение из 300 кириллических символов возвращало
`{"ok":false,"error":"json_encode"}`. Причина — двойная ошибка:

1. В `ChatService` обрезка `substr($text, 0, 240)` резала многобайтовый
   символ на середине, оставляя невалидный UTF-8.
2. Следующий «трим» хвостовых байт отрезал ещё больше, но граница уже была
   потеряна — строка оставалась битой.
3. `json_encode()` возвращал `false`, и `Response::json` подставлял
   бесполезную заглушку.

Исправлено на трёх уровнях:
- `ChatService::limitUtf8()` — обрезка идёт **от начала**, копит только целые
  символы (1–4 байта), битые байты пропускает;
- `Response::json()` при `json_encode === false` теперь чистит данные
  (`scrubUtf8`), затем повторяет кодирование с `JSON_INVALID_UTF8_SUBSTITUTE`
  и логирует причину, вместо молчаливой заглушки;
- константа `MAX_LEN = 240` вместо магических чисел.

Проверено: 300 символов «Ж» → 240 символов, `ok: true`; 300 эмодзи → OK.

## Высокая: регистр логинов

MySQL сравнивает ник без учёта регистра (`utf8mb4_unicode_ci`), SQLite — с
учётом. Из-за этого в превью заводились `demo`, `Demo` и `DEMO` как разные
игроки, а на проде те же данные вели бы себя иначе.

Исправление: `AuthService::normalizeNick()` + проверка уникальности по всем
записям и запасной поиск при входе. Теперь `DEMO` при существующем `demo` →
«Такой логин уже занят», а вход `Demo`/`demo` находит один и тот же аккаунт.

## Средние

**13. HEAD → 404.** Роутер сравнивал метод строго. Теперь `HEAD`
обслуживается как `GET`, но `Response::send()` не отдаёт тело — как требует
стандарт. Нужно для мониторинга и кэширующих прокси.

**14. Неизвестный канал чата** возвращал `ok: true` и пустой список —
пользователь видел «пустой чат» вместо ошибки. Теперь `400`
`chat_channel`, отрицательный `after` зажимается в 0.

**15. Нет лимита тела.** 2 МБ JSON принимались и разбирались. Добавлен
`Request::MAX_BODY = 1 MiB` и проверка в `Router::dispatch()` до разбора:
ответ `413 too_large`.

**16. Накопление данных.** Каждая анонимная загрузка страницы создавала
строку в `sessions`, каждый бой — в `battles`; чистки не было. Добавлен
`Migrator::gc()`: удаляет сессии старше `SESSION_TTL`, завершённые бои старше
суток, попытки входа старше суток. Запускается с вероятностью 1/50 на запрос
(и принудительно через `gc(true)` в тестах), ошибки уборки не роняют запрос.

**17. Битый UTF-8** из любого источника (не только чата) теперь не убивает
ответ: см. `Response::json()` выше.

## Проверено во втором проходе и в порядке

| Сценарий | Результат |
|---|---|
| Гонка при покупке: 6 параллельных при 500 адены | 1 успех, адена 50, в минус не ушла |
| Гонка: 10 параллельных ударов до победы | ровно 1 `won`, награда один раз |
| Регистр ников: `DEMO`/`dEmO` при существующем `demo` | отказ |
| Чат 300 «Ж», 300 эмодзи | 240 символов, `json_encode` OK |
| `after=-100`, `after=abc` | зажимается в 0, без ошибок |
| Продажа `qty=0` / отрицательное | кламп в 1 |
| `move` с городом не из списка | сбрасывается в `Giran` |
| Покупка несуществующего / не по уровню | понятные ошибки |
| Логаут | сессия уничтожена, аккаунт не виден |
| Офлайн-реген (сутки простоя) | не более 60 с за расчёт, «пачки» нет |

# Третий проход (iframe-режим, прод-конфигурация, типы входных данных)

Дата: 2026-11-27. Проверялись резервный путь сессии без cookie, запуск с
`SEED_DEMO=0`, миграция старой базы и приведение типов из JSON.

## Итог третьего прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 18 | `?s=` fallback не работал: сервер искал `miniage_sid`, клиент слал `s` | **Критический** | исправлено |
| 19 | `SEED_DEMO=0` отключал ВСЮ инициализацию — игра без предметов и мобов | **Критический** | исправлено |
| 20 | Легаси-редиректы теряли `?s=` — сессия обрывалась в iframe | Высокая | исправлено |
| 21 | `equip:"false"` (строка) приводился к `true` — предмет надевался вместо снятия | Средняя | исправлено |
| 22 | `text={...}` попадал в чат как слово «Array» | Средняя | исправлено |
| 23 | `loadZone` падал с TypeError при `state.char === null` | Низкая | исправлено |
| 24 | Деление на ноль в HUD при `hp_max = 0` | Низкая | исправлено |
| 25 | Магазин не обновлялся после покупки | Низкая | исправлено |

## Критический: резервная сессия не работала

Клиент (`api.js`, `PageController`) передаёт sid коротким параметром `?s=`,
а `Session::start()` искал только `?miniage_sid=`. Резервный путь **не
срабатывал никогда**. В обычном браузере это незаметно (работают cookie и
заголовок), но в iframe с заблокированными cookie — то есть в превью и
приватном режиме — игра была недоступна: каждая загрузка давала новую
сессию, вход «терялся».

Исправление: принимаются оба имени (`s` и `miniage_sid`), выставлен
`in_url = true`. Проверен полный сценарий без cookie: страница → bootstrap →
вход → персонаж → бой → чат.

## Критический: `SEED_DEMO=0` ломал игру

`Migrator::seed()` начинался с:

```php
if (Config::get('SEED_DEMO', '1') !== '1') {
    return;   // отключает ВСЁ
}
```

а `.env.example` и `SECURITY.md` советуют для прода `SEED_DEMO=0`. В итоге на
проде не создавались уровни, предметы, монстры и новости — игра пустая.

Исправление: `seed()` всегда создаёт контент (уровни, предметы, мобы,
новости), а флаг влияет только на демо-аккаунты. Добавлен `seedNews()`.

Проверено с `APP_ENV=production, SEED_DEMO=0`: `level_exp` 50, `items` 14,
`mobs` 10, `news` 2, `accounts` 0; регистрация и стартовый набор работают.

## Высокая: редиректы теряли sid

`gorod.php?s=…` → `/?panel=map` без `s`. В iframe это обрывало сессию на
любой старой ссылке. Теперь `s` переносится (с валидацией формата).

## Средние: приведение типов

**`equip:"false"`.** `(bool) 'false'` в PHP — это `true`, поэтому строка
`"false"` **надевала** предмет вместо снятия. Клиент шлёт настоящий boolean,
но любой другой клиент/скрипт попадал в ловушку. Добавлен `toBool()`:
принимает `bool`, `0/1`, `'true'/'false'/'on'/'yes'`.

**`text={...}`.** `(string)` от массива в PHP 8 даёт `"Array"` (с warning),
и в чат попадало слово «Array». Добавлены `Request::str()` и
`Request::intInput()`: не-скаляры превращаются в пустую строку/0, все
обработчики переведены на них.

## Низкие (клиент)

- `loadZone` читал `state.char.level` без проверки на `null` → `TypeError`,
  если зона грузится до входа.
- `updateHud` делил на `hp_max`/`mp_max` без защиты — при 0 получался `NaN`
  в `style.width`.
- После покупки магазин не перерисовывался: экран показывал старые данные,
  хотя аде­на уже списана.

## Проверено в третьем проходе и в порядке

| Сценарий | Результат |
|---|---|
| Миграция старой БД без `won_at` | колонка добавлена, старые победы заполнены |
| Повторный `migrate()` | идемпотентен |
| `?s=<script>`, `?s=abc` | отклоняются, гость |
| Полный iframe-путь без cookie | вход, персонаж, бой, чат — OK |
| `equip:true` / `equip:"false"` / `equip:0` | корректно |
| `text={...}`, `mob_id={...}` | пустая строка / 0, без «Array» |
| SQL-специфика | только PDO-параметры, `PRAGMA` только в миграции |
| MySQL vs SQLite типы | схемы согласованы |
| `display_errors` | выключен, путей в ответах нет |

# Четвёртый проход (многопользовательская логика и баланс)

Дата: 2026-11-27. Проверялись сценарии с несколькими игроками, таймеры
респавна, боевой баланс и устойчивость к переполнениям.

## Итог четвёртого прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 26 | Респавн монстра был персональным — два игрока фармили одного моба бесконечно | **Критический** | исправлено |
| 27 | `respawn_in` показывал фиктивное число (остаток от деления `time()`) | Средняя | исправлено |
| 28 | Слабые монстры наносили ровно 1 урона — старт без риска | Средняя | исправлено |

## Критический: у каждого игрока был свой респавн

`isMobAlive()` фильтровал бои по `char_id = ?`:

```sql
WHERE char_id = ? AND mob_id = ? AND state = 'won'
```

То есть таймер возрождения считался **для конкретного персонажа**. Второй
игрок видел монстра живым сразу после того, как его убил первый, и мог бить
его без ожидания. В MMO это ломает всё: одного моба можно фармить
параллельно неограниченным числом игроков.

Проверено вживую: игрок A убивает слизня → игрок B сразу начинает бой с ним
же (`ok: true`).

Исправление: респавн стал «мировым» — решение принимается по последней победе
над этим монстром **любого** игрока:

```sql
WHERE mob_id = ? AND state = 'won' AND won_at IS NOT NULL
ORDER BY won_at DESC, id DESC LIMIT 1
```

Добавлен `respawnIn(int $mobId)`. Проверено: после победы A игрок B получает
«Монстр ещё не возродился», после истечения таймера — оба снова могут бить.

## Средняя: фиктивный таймер

`mobsInZone()` считал `respawn_in` как остаток от деления текущего времени
на `respawn_sec` — то есть произвольное число, не связанное с фактическим
моментом смерти. Клиент показывал одно, сервер блокировал по другому.
Теперь `respawn_in` берётся из `respawnIn()`.

## Средняя: нерабочий урон слабых монстров

Формула `max(1, round(atk * 0.85..1.15 - def * 0.45))` при защите героя
22 (14 база + 8 доспех) давала:

| Монстр | atk | урон |
|---|---|---|
| Зелёный слизень | 6 | **1** |
| Полевая крыса | 9 | **1** |
| Красный кобольд | 14 | 2–6 |
| Степной волк | 20 | 7–13 |

Первые два уровня были полностью безрисковыми: зелья не нужны, смерть
невозможна, механика реанимации недостижима.

Исправление: защита срезает **процент** урона, а не вычитается целиком
(не более 60 % для монстра и 55 % для игрока). Теперь:

| atk | старый урон | новый урон |
|---|---|---|
| 6 | 1 | 4 |
| 9 | 1 | 7 |
| 14 | 4 | 10 |
| 20 | 10 | 15 |
| 55 | 45 | 40 |
| 110 | 100 | 81 |

Урон игрока по сильным монстрам тоже вырос (по дракону с def 48: 9 → 13),
поэтому поздние зоны не стали непроходимыми.

Проверено симуляцией:
- новичок 1 ур., 40 боёв без зелий → 32 победы, 0 смертей, HP проседает
  до 70/194, к 4 уровню 5110 адены (игра проходима, риск растёт);
- персонаж 10 ур. на Перевале Смерти → смерть на 3-м бою, `hp=0`,
  `losses=1` (механика реанимации проверяема в бою).

## Критический: мёртвый фармил во втором бою

`attack()` проверял состояние боя, но **не проверял HP персонажа**. Лимит в
3 активных боя позволял: начать бой A, начать бой B, погибнуть в A
(`hp = 0`, бой `lost`), а затем продолжать бить в B. Удары проходили, опыт и
адена начислялись — смерть фактически ничего не стоила.

Проверено харнессом (T23): после `hp = 0` удар и в своём, и во втором бою
отклоняется — «Персонаж мёртв — нужна реанимация».

## Высокая: лечение было бесплатным

`heal()` брал 500 адены только за реанимацию мёртвого. Живой персонаж мог
в любой момент получить полный HP/MP бесплатно, прямо из панели персонажа.
Из-за этого зелье лечения (450 адены за 120 HP) не имело смысла, а риск в
бою исчезал: после каждого удара — бесплатный полный отхил.

Теперь цена пропорциональна недостающему здоровью: **0,5 адены за единицу
HP/MP**, реанимация — 500. Полный хил новичка (120 HP + 60 MP) стоит 90 адены,
то есть зелье по-прежнему выгоднее по HP, но не восстанавливает ману и не
лечит «всё сразу». Отдых без денег остаётся доступен — пассивная регенерация.

## Высокая: гонка хода (MySQL)

`attack()` читал строку боя **до** транзакции:

```php
$battle = Database::one("SELECT * FROM battles WHERE id = ? AND char_id = ?", ...);
return Database::transaction(function () use ($battle, ...) { ... });
```

php-wasm однопоточный, поэтому в превью это не проявлялось. На MySQL два
параллельных удара получали одинаковые `mob_hp`, `turn` и `log_json`, и
второй перезаписывал первого: ходы терялись, а победа могла начислиться
дважды.

Исправлено двумя мерами:
- строка перечитывается **внутри** транзакции с `SELECT ... FOR UPDATE`
  (для SQLite конструкция опускается — там писатели и так сериализованы);
- ход захватывается условным UPDATE: `SET turn = turn + 1 WHERE turn = <прочитанный>`.
  Если строку изменил конкурент, `rowCount()` вернёт 0 и удар отклоняется
  («Ход уже сделан»).

Проверено харнессом (T24): `turn` увеличивается ровно на 1 за удар.

## Средняя: гонка при создании сессии

`Session::ensureRow()` делал `SELECT`, затем `INSERT`. Два параллельных
запроса с одним новым sid (страница + bootstrap при первой загрузке) оба не

Проверено: 8 параллельных bootstrap с одним новым sid → 8/8 `ok:true`.

## Низкие

`null` даёт 0, и персонаж уезжал в левый верхний угол карты. Теперь

# Шестой проход (пароли, персистентность, брошенные бои)

Дата: 2026-11-27. Проверялись длинные пароли, сохранение БД между
запросами, антиспам регистрации и «залипшие» активные бои.

## Итог шестого прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 36 | Пароль >72 байт обрезался — вход по чужому паролю | **Критический** | исправлено |
| 37 | Изменения не попадали на диск сразу (WAL) — терялись при рестарте | **Критический** | исправлено |
| 38 | Брошенные бои навсегда блокировали старт новых | Высокая | исправлено |

| 41 | `accounts.ip` не заполнялся вовсе — антиспам был бы мёртвым | Средняя | исправлено |

## Критический: обрезка пароля до 72 байт

`password_hash()` с bcrypt **молча** обрезает пароль на 72 байтах.
Регистрация принимала до 200 байт, поэтому пароль

```
AAAA…(72 байта) + "TAILONE"
```

и

```
AAAA…(72 байта) + "СОВСЕМ-ДРУГОЙ-ХВОСТ"
```

давали **одинаковый хеш**. Проверено вживую до фикса: вход с другим
хвостом после 72-го байта пускал в аккаунт.

Исправление:
- `AuthService::passwordBytes()` — лимит по фактическому алгоритму
  (bcrypt → 72 байта, argon2id → 4096);
- регистрация отказывает, если пароль длиннее лимита, вместо тихой обрезки;
- перехеширование в `login()` делается только при пароле в пределах лимита,
  иначе «улучшение» хеша обрезало бы пароль и ломало вход;
- длина считается в **байтах**, а не символах: кириллица — 2 байта на букву,
  поэтому 40 русских букв уже переполняют bcrypt.

## Критический: данные не сохранялись на диск

SQLite работал в режиме WAL: свежие коммиты живут в файле `-wal`, а
основной `.sqlite` дописывается при закрытии соединения. Preview-мост
сохраняет на диск именно основной файл, поэтому последние изменения
(регистрация, бой, покупка) **не попадали в снимок** и терялись при
рестарте сервера.

Проявлялось коварно: `pullDb()` копировал файл, в котором не было
последнего коммита, и данные «отставали на один запрос». Проверено: 3
регистрации подряд → на диске каждый раз на один аккаунт меньше.

Исправление: `Database::checkpoint()` (`PRAGMA wal_checkpoint(TRUNCATE)`)
вызывается мостом после каждого запроса, до сохранения снимка. Плюс
`pullDb()` больше не глотает ошибки молча — пишет в лог.

## Высокая: брошенные бои блокировали игру

Лимит — 3 активных боя, но клиент при входе восстанавливает **только
последний** (`battle/current` → `ORDER BY id DESC LIMIT 1`). Начав три боя и
закрыв вкладку, игрок навсегда получал «Слишком много активных боёв»:
двух боёв он даже не видел.

Проверено вживую: 3 старта → реконнект показывает 1 → новый бой невозможен.

Исправление:
- `closeStaleBattles()` — бои без хода дольше 30 минут закрываются как
  «прерваны» (без награды и без поражения), вызывается при старте боя;
- `battle/current` отдаёт массив `battles` (все активные), поле `battle`
  оставлено для совместимости;
- клиент, если боёв несколько, показывает предупреждение.

## Высокая: регистрация без ограничений

Антифлуд был только у входа (`login_attempts`), у регистрации — ничего.
Скрипт мог создать тысячи аккаунтов; каждый — `password_hash` (argon2id,
в превью ~50 мс CPU, в проде сопоставимо). Проверено: 5 регистраций подряд
проходили свободно.

Исправление: 5 регистраций в час с одного IP и 300 в сутки всего. В
`APP_ENV=testing` ограничение выключено, чтобы не мешать харнессу.

## Средняя: `ip` стирался при входе

`AuthService::login()` делал `'ip' => ''` — то есть после любой
авторизации адрес обнулялся. А регистрация сразу логинит, поэтому у
новых аккаунтов IP был пустым всегда, и лимит по IP был бы мёртвым.

Теперь в `ip` пишется `Request::currentIp()` (учитывает `X-Forwarded-For`).

## Средняя: `ip` не заполнялся при создании

`Migrator::createAccount()` вообще не писал колонку `ip`, хотя она есть в
обеих схемах. Добавлено заполнение.

# Седьмой проход (многопользовательский бой и уборка)

Дата: 2026-11-27. Проверялись одновременные действия двух игроков на одном
мобе, брошенные бои и сборка мусора.

## Итог седьмого прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 42 | Двое били одного моба — награда дублировалась | **Критический** | исправлено |

| 44 | Сборка мусора почти никогда не запускалась | Средняя | исправлено |

## Критический: один моб — две победы

`isMobAlive()` проверял только прошлые **победы**. Активный бой не
учитывался, поэтому второй игрок мог начать бой с мобом, которого уже
бьёт первый. Проверено вживую: A и B одновременно начали бой со слизнём,
A добил — и B тоже добил **того же** моба; у обоих `wins=1`, обоим
начислены опыт и адена. Один моб кормил двоих.

Исправление:
- `isMobBusy($mobId, $charId)` — моб занят, если его бьёт **другой**
  игрок (свои бои не считаются, иначе игрок не мог бы вернуться в бой);
- проверка занятости повторяется **внутри транзакции** вместе с `INSERT`
  боя: между проверкой и вставкой на MySQL успевал вклиниться второй игрок;
- в зоне моб показывается полем `alive=false, busy=true` и таймером
  респавна, а не «живым»;
- на канвасе подпись «бьётся с другим игроком» вместо «респавн ~Ns» —
  иначе игрок думал, что таймер врёт;
- после `flee` моб сразу освобождается для других.

## Высокая: брошенный бой держал моба

`isMobBusy()` учитывал любой активный бой. Если игрок закрыл вкладку,
моб оставался «занятым» навсегда для всех остальных. Теперь занятость
считается только по свежим боям (ход не позже 30 минут назад), а
`closeStaleBattles()` вызывается ещё и из `bootstrap` — уборка не зависит
от того, начнёт ли игрок новый бой.

## Средняя: сборка мусора не работала

`gc()` начинался с `static $done`, который живёт одну обработку запроса.
Под PHP-FPM каждый запрос — новый процесс, поэтому флаг всегда был `false`,
но шанс `random_int(1, 50) === 1` «съедался» на текущем запросе, а
следующий начинал заново. На практике таблицы `sessions`, `battles` и
`login_attempts` не чистились никогда.

Проверено: 10 анонимных запросов → +9 строк в `sessions`, ни одного
удаления. Теперь достаточно случайной выборки на запрос: в среднем одно
срабатывание на 50 запросов, независимо от модели процессов.

|---|---|
| A начинает бой с мобом | `ok, id=1` |
| B пробует того же моба | «Монстра уже атакует другой игрок» |
| B видит моба в зоне | `alive=false busy=true respawn=15` |
| A видит того же моба | `alive=true busy=false respawn=0` |

| B после отступления A | `ok, id=2` |

## Критический: 32-битное переполнение адены

`PHP_INT_SIZE` в этой сборке php-wasm равен **4** (32 бита), то есть
`PHP_INT_MAX = 2 147 483 647`. Колонки в схемах объявлены `BIGINT`/`INTEGER`,
SQLite отдаёт большие суммы строкой — но код приводил их к `int`:

```php
foreach ([... 'adena' ...] as $k) { $char[$k] = (int) $char[$k]; }
```

Проверено: баланс 9 000 000 000 читался как **2 147 483 647**, и вся
дальнейшая арифметика шла по обрезанному значению — деньги просто исчезали.
Покупка на 44 550 списывалась с обрезанного числа.

Обратный каст после `round()` не спасает: `(int) round(9000000000.0)`
даёт **410 065 408** (переполнение double → int по модулю 2^32).

Исправление: `adena` и `exp` больше не приводятся к `int`, значение
остаётся `double` — он держит 53 бита точно, чего с запасом хватает для

| 50 | Лог боя рос безгранично и целиком шёл в каждом ответе | Средняя | исправлено |

## Критический: вход за чужого персонажа

`AuthService::character()` искал персонажа по одному `id` из сессии:

```php
$char = Database::one("SELECT * FROM characters WHERE id = ?", [(int) $charId]);
```

Владелец не проверялся. Воспроизведено: в сессию аккаунта B подставлен

путь через `accounts.active_char`: если там окажется чужой id, подстановка
сработает так же.

Формально сессию подделать нельзя (она серверная), но дыра реальна в двух
случаях: id переиспользуется после удаления записи, и `active_char` остаётся
от удалённого персонажа. Проверка владельца — обязательный инвариант, а не
защита от подделки cookie.

Исправление: `SELECT ... WHERE id = ? AND account_id = ?`, владелец берётся
из `account()`. Проверено вживую: чужой `char_id` → отказ, свой → работает,
чужой `active_char` → отказ, `selectCharacter` чужого → отказ.

`buy()` обрезал `qty` до 99 **на одну покупку**, но стак рос без учёта уже
лежащего:

```php
Database::update('inventory', ['qty' => (int) $row['qty'] + $qty], ...);
```

Купил 99, купил ещё 99 — в одной ячейке **198** зелий.

Исправление: лимит `MAX_STACK = 99` действует на весь стак. Если места
меньше запрошенного — продаётся ровно столько, сколько помещается, и
списывается плата **только за них**; в полный стак — понятный отказ.

Проверено: 5 (стартовый набор) + 60 = 65, докупка 99 → 99 (выдано 34,
оплачено 34 × 450 = 15 300), третья покупка отклонена, ячейка одна.

Обрезка в трёх местах: при атаке, при отступлении и при чтении состояния
(страховка для боёв, записанных раньше). Проверено: 85 ходов — 60 строк,
ответ 3.5 КБ вместо 9.5 КБ.

# Десятый проход (атомарность транзакций, ключ лимита входа, регистр ника)

Дата: 2026-11-27. Взяты два известных незакрытых пункта (неатомарный
`battle/start`, гонки на SQLite) плюс область аутентификации.

## Итог десятого прохода

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 51 | `login_attempts` раздувалась длинными никами, на MySQL ломала вход | Высокая | исправлено |
| 52 | Транзакции на SQLite открывались как DEFERRED | Средняя | исправлено |
| 53 | `normalizeNick` не обрабатывал кириллицу без mbstring | Низкая | исправлено |

## Высокая: ключ лимита входа не ограничен по длине

`recordFailedLogin()` писал в `login_attempts` ключ из ника **как есть**.
Проверено: вход с ником в 5000 байт создавал строку ровно такого размера.
Каждая неудачная попытка с новым ником добавляла строку — таблицу можно
раздувать бесконечно, а `gc()` её не чистит (нужна блокировка истекла).

На MySQL это ещё и функциональная поломка: `nick` объявлен
`VARCHAR(64)`, и длинный ключ даёт ошибку усечения. То есть **любой** вход
с длинным ником падал бы с 500 вместо честного «неверный логин».

Исправление: ключ длиннее 48 байт сжимается до `substr(0, 40) + '#' +
sha1(...)7` — укладывается в колонку и не сливает разные длинные ники
(проверено: два ника, различающихся в 900-м байте, дают разные ключи).

## Средняя: DEFERRED-транзакции на SQLite

`PDO::beginTransaction()` на SQLite открывает **DEFERRED**-транзакцию:
блокировка записи берётся только на первом `INSERT`/`UPDATE`. Между
проверкой «моб свободен» и вставкой боя (внутри одной транзакции!) два
процесса успевают оба прочитать состояние, и один получает `SQLITE_BUSY`
уже после проверки.

Исправление: корневая транзакция открывается как `BEGIN IMMEDIATE` —
блокировка записи берётся сразу, и проверка с вставкой становятся
атомарными относительно другого процесса. Вложенные транзакции попрежнему
через `SAVEPOINT`. Откат защищён от двойной ошибки.

Проверено: вложенные транзакции, откат внутренней, откат внешней,
повторная транзакция после сбоя, покупка с исключением внутри — все
сценарии корректны. Отдельно: в превью гонки нет и не было — там один
процесс PHP на все запросы (единственный `PhpNode` в мосте), поэтому
запросы физически последовательны. На PHP-FPM+MySQL это была реальная
дыра, и её закрывает транзакция с блокировкой на уровне БД.

## Низкая: регистр кириллицы без mbstring

`normalizeNick()` полагался на `mb_strtolower`, а при его отсутствии —
на `strtolower`, который **не трогает кириллицу**: `strtolower('Демо')`
возвращает `'Демо'`. В этой сборке mbstring нет.

Эксплуатация ограничена: ники валидируются как `[A-Za-z0-9_-]{3,16}`,
поэтому кириллицу в ник не вписать. Но нормализация используется и для
сравнения, и для ключей лимита — полагаться на «сейчас не проскочит» в
функции безопасности неправильно.

Исправление: своя таблица «заглавная → строчная» для русских букв через
`strtr` (не требует ни mbstring, ни intl), с сохранением ветки mbstring,
если расширение есть. Для латиницы поведение не изменилось: `DEMO` и
`demo` теперь один ключ (проверено: 4 неудачи разными регистрами →
1 ключ, счётчик 4).

## Проверено и в порядке

| Сценарий | Результат |
|---|---|
| Вложенные транзакции (savepoint) | коммит внутренней сохраняется |
| Откат внутренней транзакции | внешние изменения живы |
| Откат внешней транзакции | изменения отброшены |
| Транзакция после ошибки | работает снова |
| Покупка с отказом внутри транзакции | адена и инвентарь не тронуты |
| Вход в верхнем регистре ника | принят (`DEMO` → demo) |
| Ник 500 символов | вежливый отказ, сервер жив |
| Блокировка после 5 неудач | верный пароль тоже отклоняется |

## Критический: конфиг из корня файловой системы

`Config::load()` последним читал `/config.json` и принимал **любые** ключи
без ограничений. Воспроизведено: файл с `DB_PASS` и `APP_ENV` подменял

Файл нужен только preview-мосту (php-wasm), где нет ни `.env`, ни
переменных окружения. В проде его быть не должно — но раз код его читает,

1. файл читается только при `MINIAGE_WASM` (флаг превью);
2. ключи проходят через белый список — берутся только те, что уже есть в

Проверено: в проде файл игнорируется полностью; в wasm принимаются только
разрешённые ключи, а `DB_PASS`/`APP_ENV`/`SEED_DEMO_PASS` остаются из `.env`.

## Критический: лимит по IP обходился заголовком

`Request::currentIp()` брал **первое** значение `X-Forwarded-For`, если
заголовок присутствовал, — без проверки источника и без валидации. Это
значение пишется в `accounts.ip` и используется в лимите «5 регистраций в
час с адреса».

Воспроизведено: 7 регистраций подряд, каждая с новым `X-Forwarded-For` —
все прошли, в `accounts.ip` легли `10.0.0.1 … 10.0.0.6`. Лимит не работал
вообще.

Исправление:

1. `Request::currentIp()` читает `X-Forwarded-For` **только** если
   `REMOTE_ADDR` входит в `TRUSTED_PROXIES` (новый ключ конфига, по
   умолчанию пуст);
2. значение валидируется как IP, иначе откат на `REMOTE_ADDR`;
3. preview-мост перестал подставлять заголовок в `REMOTE_ADDR` — теперь
   передаёт настоящий адрес сокета и отдельный `HTTP_X_FORWARDED_FOR`,
   чтобы PHP применил обычную политику.

Проверено: поддельный XFF не меняет IP (всегда `127.0.0.1`), 7 регистраций
с разными заголовками упираются в лимит, в `accounts.ip` только настоящий
адрес. С доверенным прокси (`TRUSTED_PROXIES=10.0.0.2`): реальный IP
клиента из заголовка, мусор в заголовке → откат на `REMOTE_ADDR`.

# Тринадцатый проход (сессии: TTL, HTTPS-cookie, контракт Request::get)

Дата: 2026-11-27. Проверялся жизненный цикл сессии и контракты Request.

| # | Баг | Серьёзность | Статус |
|---|---|---|---|
| 59 | `X-Forwarded-Proto` подделывался клиентом → cookie без `Secure` | Высокая | исправлено |

| 61 | `Request::get()` с числовым дефолтом ронял запрос в 500 | Средняя | исправлено |

## Критический: сессия не истекала никогда

В файловом режиме (php-wasm, а также любой хостинг без записи нативных
сессий) `loadFileData()` читала `data_json` **без проверки `last_used`**.

Проверено: сессия с `last_used` 30-дневной давности при `SESSION_TTL=86400`
продолжала возвращать `account_id` — то есть любой, кто сохранил sid
(украденная cookie, запись в логах, общий компьютер), входил в аккаунт
спустя месяцы.

Исправление: `loadFileData()` проверяет `last_used` через `expired()`,
просроченная строка удаляется и сессия считается пустой. Порог —
`SESSION_TTL` (не меньше 60 с).

Проверено на границах: возраст 0 / 1 ч / 12 ч / 23.9 ч — сессия жива;
24 ч + 5 с и 30 дней — истекла, строка удалена.

## Высокая: HTTPS определялся по заголовку от клиента

`isHttps()` возвращал true при любом `X-Forwarded-Proto: https`. Заголовок
подконтролен клиенту, поэтому на HTTP можно было заставить сервер выдать
cookie **без** флага `Secure` (и наоборот — заголовок от постороннего
влиял на политику cookie).

Исправление: заголовок учитывается только от адреса из `TRUSTED_PROXIES`;
прямой `$_SERVER['HTTPS']` работает как раньше.

Проверено: `XFP: https` от клиента → `isHttps=false`; от доверенного
прокси → `true`; прямой HTTPS → `true`.

## Средняя: числовой дефолт в Request::get() — фатальная ошибка

Подпись `get(string $key, ?string $default = null)` в strict_types
запрещала числовой дефолт. Вызов `$req->get('age', 0)` давал
`TypeError` → PHP падал → мост отдавал 500 и писал в лог
`PHP не вернул ответ: Uncaught TypeError`. Нашлось на живой проверке:
диагностический параметр уронил бы весь эндпоинт (и так было бы с любой
опечаткой в контроллере).

Исправление: `mixed $default`, поведение прежнее — скаляр приводится к
строке, иначе дефолт как строка или `null`.

## Замечание по методике

Проверка TTL в живом превью оказалась невозможной: БД превью живёт в
виртуальной ФС php-wasm (`/var/miniage.sqlite`), и правки файла на диске
хост-машины PHP не видит. Все выводы по сессиям подтверждены
офлайн-харнессом, где БД настоящая. Это ограничение среды, а не игры.

## Проверено и в порядке

| Проверка | Результат |
|---|---|
| `Database::quoteIdent` | имена таблиц/колонок валидируются регуляркой |
| `Session::ensureRow` на гонке | повторная проверка после UNIQUE-ошибки |

| Ротация sid при логине | клиент получает новый sid в ответе |
